0 · Executive summary

ePassi is implemented as a redirect / hosted-form-post gateway. The lifecycle is:

  1. RX renders the CAPS pay element from the caps-ui package; the user clicks Pay.
  2. caps-ui (EpassiElement) calls caps-be POST /create-order.
  3. caps-be (createEpassi) mints a UUID STAMP, inserts a caps.pg_transactions row at status 1 (signature_created), builds and SHA-512-signs an EpassiForm.
  4. caps-ui receives the signed form and auto-submits it to the ePassi Payment Button.
  5. The user pays on ePassi.
  6. ePassi notifies CAPS-BE on two independent paths: the browser RETURN redirect (STAMP/PAID/MAC) and a server-to-server webhook to NOTIFY_URL.
  7. RX polls GET /check-status/:id, which calls ePassi's verification API (/api/e2/passports/exist).
  8. CAPS-BE pushes final status to RX / external endpoints via processExternal.
Reliability model. The integration is deliberately idempotent and multi-path: the redirect, the webhook and the verification check can all finalise the same transaction, and any transaction already in a final state is ignored (internal_cycle_closed).
Environment note — ePassi is not seeded locally. The local database snapshot contains zero ePassi rows in caps.payment_gateways, caps.pg_type and caps.pg_status (verified: 0 rows each). The supabase/…_data.sql seed lists 18 gateways but not ePassi. All code and status constants exist; a deploy requires an operator to insert the gateway, pg_type and matching pg_status rows. See §7.2.

1.2 Routing in caps-be

POST /create-order (caps-be/src/routes/create-order.ts):

  1. processOrder(body) → vendor: case "epassi": vendor = new VendorEpassi(vendorConfig, order.currency) (processOrder.ts:203-204).
  2. vendor.create(order, req) → createEpassi(config, order).
  3. Responds { data: data.response } = { data: EpassiForm }.
  4. Then processExternal(entity, status, transaction) pushes the created event to RX (fire-and-forget, processFailure fallback).

2 · Payment Initiation

ePassi is not reached by a server redirect; the storefront auto-POSTs a hidden HTML form.

export const EpassiPaymentForm = ({ formData, siteUrl }) => {
  const formElement = useRef(null);
  useEffect(() => { formElement.current?.submit(); }, []);
  return (
    <form action={siteUrl} method="post" ref={(x) => (formElement.current = x)}>
      {Object.entries(formData).map(([name, value]) =>
        value == null ? null : <input key={name} type="hidden" name={name} value={String(value)} />
      )}
    </form>
  );
};

EpassiElement.tsx mounts it with siteUrl = gateway.test ? getEpassiTestApiUrl() : getEpassiProdApiUrl().

istatus normalises numbers → strings: 0→failed, 1→created, 4→canceled, 6→succeeded. isEpassiFinalStatus = {0,4,6}.

3.2 Status-check API

GET /check-status/:id → processStatusRequest builds new VendorEpassi(vendorConfig) → checkStatusEpassi:

  1. Credential guard → INTERNAL_SERVER_ERROR if username/password missing.
  2. Short-circuit if final status or no visibleId:
    • terminateStaleTransactions && !visibleId && status===1 → fail with "Orphan Transaction";
    • otherwise return current local status (nothing to verify without PAID).
  3. Verification API verifyEpassiPayment: api_password = SHA512(PAID & MAC_KEY & SITE_LOGIN); GET …/api/e2/passports/exist?api_login=<SITE>&api_password=<hash>&id=<PAID>&site_login=<SITE>. Returns true/false, or "unknown" on network error / non-OK.
  4. Decision: "unknown" → local status; stale+not-found → failed; found → epassi_successful (6); else local status.
In the route the call is vendor.status(trxnData, false, terminateStaleTransactions) — updateInternalTable=false, so this path computes status without persisting (transaction: null). Persistence happens via redirect/webhook/orphan.

3.3 Status in RX

RX has no ePassi-specific code. confirm-payment.tsx calls checkStatus() from caps-ui, which does GET /check-status/:id. Because CAPS normalises numbers through istatus, RX compares generic strings against rx/src/constants/PaymentStatus (created/succeeded/failed/canceled) and needs no ePassi awareness. RX consumes the packaged UI via "caps-ui": "file:caps-ui-2.3.1.tgz".

4 · Webhook Implementation

Endpoint: POST /webhooks/:id (routes/notify.ts; mounted at /webhooks in routes/index.ts). :id = config.id, exactly the id embedded in NOTIFY_URL.

POST /webhooks/:id  { STAMP, PAID, MAC, errors? }

4.1 Validation pipeline (update.ts)

#StepResult on failure
1Parse body as EpassiWebhookNotification—
2notification.errors present400 webhook_error
3STAMP + PAID + MAC all present400 webhook_error
4MAC = SHA512(STAMP & PAID & MAC_KEY), timingSafeEqual401 signature_issue
5fetchTransaction(stamp, config.id) — STAMP is the CAPS UUIDerror path
6Idempotency: already final → ignore200 internal_cycle_closed
7Update → status=6, visibleId=paid, failureMessage=null—
8Audit Epassi payment status updated; respond 200 {data:"ok"}; then processExternal—
Nuance: step 6 returns an error string with HTTP OK. In notify.ts there is no data, so the route replies 200 {error:"internal_cycle_closed"} and skips processExternal. ePassi treats 200 as acknowledged.

4.2 Idempotency & duplicate events

  • Duplicate deliveries are safe: the final-status guard short-circuits the second one.
  • The webhook cannot un-finalise a transaction the redirect already finalised (and vice-versa) — both use the same guard.
  • There is no separate event-id dedupe store; the transaction status is the dedupe key.

The webhook and the redirect are ordering-independent: both verify the MAC and both set visibleId = PAID; whichever arrives first finalises, the other is ignored.

5 · Redirect Flow

5.1 Route (routes/redirect.ts — ALL /redirect/:pgType?)

For POST, ePassi merges query + body so PAID (body) survives alongside caps_transaction_id/pg_id (query):

if (pgType === "epassi") {
  params = { ...(req.query as QueryParams), ...(req.parsedBody as QueryParams) };
}

After the processor returns, it appends caps_transaction_id=<id> to the merchant returnUrl, sets the Location header, persists the merged params into pg_transactions.redirectRequest, and emits an audit event.

The redirect route does not call processExternal — RX learns of the final status via the webhook or its own status poll.

5.3 Success / failure / cancellation

  • Success (RETURN): ePassi appends STAMP/PAID/MAC → verified → finalised → browser redirected to order.returnUrl?caps_transaction_id=<id>.
  • Failure (REJECT): error param → epassi_failed with the raw message.
  • Cancellation (CANCEL): the CANCEL URL is identical to RETURN/REJECT; a user cancel arrives as error and is recorded as epassi_failed (0). epassi_canceled (4) only comes from the explicit cancel API.

6.4 Orphan handling

  • orphanProneVendors includes "epassi" (types/orphan.ts:84).
  • processOrphan calls vendor.status(rawTransaction, true, true).
  • A stuck signature_created with no visibleId → failed "Orphan Transaction"; a not-found passport (with terminate) → epassi_failed.
  • Stale signatures are voided via the cancel API.

7.2 Known gaps / incomplete areas

No local seed for ePassi. Zero rows in payment_gateways, pg_type and pg_status for ePassi. A deploy needs an operator to insert the gateway (username=SITE, password=MAC key, test), a pg_type row, and matching pg_status description entries.
Dead constants. epassi_pending (3) and epassi_processing (5) are declared but never written.
Cancel vs. reject indistinguishable on redirect. Both yield epassi_failed (0); only the cancel API yields epassi_canceled (4).
Redirect does not call processExternal. RX learns the final status via the webhook or its own poll.
No partial refunds. Enforced by exact-amount equality.
confirm() unsupported. Returns 400 confirm_not_needed.
EUR only. epassiCurrencyCodes = ["eur"]; processGateway gates availability on isEpassiCurrencyCode(currency).
Test/prod coupling. The test flag drives both the client POST target and the server verify/cancel target; a mismatch would break MAC/verification consistency.
No event-id dedupe store. The transaction status is the only dedupe key.
