Donations — PG Mapping Solution & Action Items

How the CAPS Admin maps a payment gateway per donation. Selecting a gateway creates a caps.pg_mapping row whose metadata carries the donation id (program_id). This page covers the solution and the two action items to implement it.

1 The donation solution

Two interacting flows: the admin fetches the gateway list for a donation project (Action Item 1), then saving a selection creates the missing mappings in caps.pg_mapping (Action Item 2).

What problem it solves

  • A donation needs its own set of payment gateways.
  • The same gateway (e.g. Stripe) may serve many donations — so it must be mapped once per donation.
  • The mapping key is (entity_id, pg_id, metadata), and metadata.program_id holds the donation id — that is what makes the same gateway legal per donation.
  • When an admin selects gateways, only the ones not already mapped for that project should be inserted (idempotent).

The two action items

① caps-ui — customFetchGateway
fetch the full configured gateway list (dropdown) ② donation-be + bx-be-nestjs — create endpoint
compare selection with existing mappings, insert the missing rows
Where the donation id goes. It is stored in caps.pg_mapping.metadata → {"program_id": <donationId>}. At checkout, caps-be matches mappings by comparing the incoming metadata (which carries the program_id) against each row's metadata — a subset match.

2 Action Item 1 — customFetchGateway in caps-ui

A new exported function in caps-ui, built exactly like the existing checkStatus and refundOrder functions: same folder shape, same customFetch/setCurrentLocale usage, same { data } / { error } return contract.

2.1  Folder shape (mirrors checkStatus / refundOrder)

A src/functions/customFetchGateway/customFetchGateway.ts A src/functions/customFetchGateway/customFetchGateway.types.ts A src/functions/customFetchGateway/index.ts M src/functions/index.ts // export * from "./customFetchGateway"

Fetches the full gateway list for the entity (no project filter) — the caller feeds the result into the Action Item 2 sync.

2.3  Types

Same contract as the siblings. It returns all gateways for the entity — no project/metadata filter here; the filtering that decides which are already mapped happens in Action Item 2.

3 Action Item 2 — donation-be + bx-be-nestjs endpoints

Two new endpoints. donation-be receives the donation id and the admin-selected paymentGatewayId and forwards them. bx-be-nestjs (the NestJS API that owns CAPS Admin) does the fetch → compare → insert-missing work. Reads use caps.vw_pg_mapping; inserts go to caps.pg_mapping.

3.1  Endpoint in donation-be

POST donation/gateway-mapping new donation-be

Receives the donation id and the gateway the admin selected (one, or an array):

{ "donationId": 1127694, "paymentGatewayId": 3, // Number(pg.pgId) selected in the admin UI (or [3, 7]) "country": "NZ", "org": 4, "module": "DN", "test": false }

Does: forwards the body to bx-be-nestjs unchanged, then returns the sync result.

// donation-be → bx-be-nestjs POST <bx-be-nestjs>/pf/caps/payment-gateways/donation-mapping { "donationId": 1127694, "paymentGatewayId": 3, "country": "NZ", "org": 4, "module": "DN", "test": false }

The id: Number(pg.pgId) value the admin selected is the payment_gateway_id — it becomes pg_mapping.pg_id.

3.2  Endpoint in bx-be-nestjs

POST pf/caps/payment-gateways/donation-mapping new @CanAccess PF::common-caps · admin

Route order. Declare the literal donation-mapping route before the :id param routes in the controller, so it is not captured as an :id.

4 The matching logic — narrow flow

The Next.js (bx-be-nestjs) endpoint takes the body from donation-be, fetches the full gateway list for the entity, compares it against the body's paymentGatewayId, and inserts a mapping only for the ids that match and are not already mapped for that donation.

4.1  The body (Next.js endpoint)

{ "donationId": 1127694, // -> metadata.program_id "paymentGatewayId": 3, // Number(pg.pgId) selected in the admin UI (or [3, 7]) "country": "NZ", "org": 4, "module": "DN", "test": false }

4.2  Narrow flow (step by step)

  1. Take the body. donationId + paymentGatewayId; the donation id becomes metadata = { program_id: donationId } for the gateway fetch and the insert.
  2. Use the custom gateway function. Call customFetchGateway() (Action Item 1) with the same country, org, module, test — it POSTs /fetch-gateways and returns the full list of configured PG for the entity.
  3. Compare the lists. Keep the fetched gateways whose id is in the body's paymentGatewayId → the ones the admin selected that CAPS actually offers.
  4. Check what is already mapped. From caps.vw_pg_mapping for this entity, take rows whose metadata.program_id === donationId → the ids already mapped for this donation.
  5. Insert only the missing. For each matched id not already mapped, INSERT into caps.pg_mapping with metadata = { program_id: donationId } and a unique sort_order.
  6. Edge case — mapping already exists with a metadata value. Do not violate UNIQUE (entity_id, pg_id, metadata): skip rows with the same (entity_id, pg_id, metadata) instead of re-inserting.

4.3  Compare table

4.4  Edge case — mapping already exists with a metadata value

Same key already present → skip, don't duplicate. The unique key is (entity_id, pg_id, metadata). Test each candidate against the rows already fetched for this donation:
  • Exact same (pg_id, metadata.program_id) exists → already mapped → add to alreadyMapped and skip (no duplicate, no unique-violation).
  • Same pg_id, different metadata.program_id → a different donation → insert (the key allows it — the same gateway serving another donation).
  • Same pg_id, metadata IS NULL row already exists → Postgres treats NULL as distinct, so the insert would still succeed; prefer matching on the program_id value (not pg_id alone) to avoid an ambiguous duplicate.
Idempotent. Re-running the endpoint inserts nothing the second time: the matched ids are already present for the donation, so missing is empty → inserted: [], alreadyMapped: [3].

4.5  Reference implementation (Next.js service)

// bx-be-nestjs — payment-gateways.service.ts async syncDonationMapping(dto: DonationMappingDto) { const ids = Array.isArray(dto.paymentGatewayId) ? dto.paymentGatewayId : [dto.paymentGatewayId]; // 2) full list of configured PG for the entity (customFetchGateway → caps-be /fetch-gateways) const fetched = await this.caps.fetchGateways({ country: dto.country, org: dto.org, module: dto.module, test: dto.test ?? false, metadata: { program_id: dto.donationId }, }); const configuredIds = new Set(fetched.map((g) => Number(g.id))); // 3) keep only the ids that are both selected AND actually configured const matched = ids.map(Number).filter((id) => configuredIds.has(id)); // 4) what is already mapped for THIS donation (match on metadata.program_id) const eid = await this.repo.resolveEntityId(dto.country, dto.org, dto.module); const existing = await this.repo.listMappings(eid); // reads caps.vw_pg_mapping const alreadyForDonation = new Set( existing .filter((r) => Number((r.metadata as Record<string, unknown>)?.['program_id']) === Number(dto.donationId)) .map((r) => Number(r.pgId)), ); // 5) insert only the missing (skip ones already mapped for this donation) const missing = matched.filter((id) => !alreadyForDonation.has(id)); if (missing.length > 0) { const nextOrder = existing.reduce((m, r) => Math.max(m, Number(r.sortOrder)), 0); await this.repo.insertDonationMappings( eid, missing.map((pgId, i) => ({ entityId: eid, pgId, sortOrder: nextOrder + i + 1, metadata: { program_id: Number(dto.donationId) }, })), ); } return { message: 'Donation gateway mappings synced successfully', data: { inserted: missing, alreadyMapped: matched.filter((id) => alreadyForDonation.has(id)), entityId: eid, donationId: Number(dto.donationId), }, }; }

Reads come from the view caps.vw_pg_mapping; writes go to the base table caps.pg_mapping (a view is read-only). To filter by project in SQL instead of in JS, add sql\`${vwPgMappingInCaps.metadata}->>'program_id' = ${String(donationId)}\` to the view query's .where(...).

6.5  Verification checklist

  1. Select [3, 7] for a fresh project → both inserted; response inserted: [3,7].
  2. Run again with [3, 7] → inserted: [], alreadyMapped: [3,7] (idempotent).
  3. Select [3, 7], then only [3] → nothing removed, nothing inserted for 3.
  4. Same pg_id on a different project → inserted (metadata differs → unique key allows).
  5. Missing entity → 404; bad DTO → 400.
  6. npm run lint, npx tsc --noEmit, npm run test:unit pass.

7 SQL & data model

7.1  No migration needed

caps.pg_mapping.metadata (jsonb) and the key UNIQUE (entity_id, pg_id, metadata) already exist — the solution adds code on top of them.

7.2  The insert (per missing gateway)

-- one row per missing gateway; metadata carries the donation project id INSERT INTO caps.pg_mapping (entity_id, pg_id, sort_order, metadata) VALUES (102, 7, 2, '{"program_id": 1127694}');

7.3  How the rows look

entity_idpg_idsort_ordermetadataMeaning
10231{"program_id":1127694}Stripe for donation project 1127694
10272{"program_id":1127694}PayPal — inserted (was missing)
10233{"program_id":1127695}same Stripe, different project — legal
10294NULLfallback — applies when nothing matches
NULL trap. Postgres treats NULL as distinct in a UNIQUE constraint, so UNIQUE (entity_id, pg_id, metadata) stops guarding whenever metadata IS NULL. Because this feature always writes {"program_id": …}, that affects only legacy/fallback rows — but making metadata NOT NULL DEFAULT '{}'::jsonb is the recommended hardening.
Checkout parity. caps-be reads the same rows at donation checkout and matches by the same rule: a row matches when every key in its metadata equals the incoming metadata (subset match), with a fallback to metadata IS NULL rows.
