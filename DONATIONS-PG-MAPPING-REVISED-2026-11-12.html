Source draft: Donations — PG Mapping Solution & Action Items (Jeeru Praveen, 11 Nov 2026). The five comments below were raised in the Slack DM on 12 Nov 2026, 07:44–07:54 IST. Each one changes the design.

Comment 1 · metadata key
“The mapping key is (entity_id, pg_id, metadata), and metadata.program_id holds the donation id — that is what makes the same gateway legal per donation.”
“It should be metadata.donation_project_id, which will hold the donation project id.”
Applied. Every occurrence of program_id is replaced with donation_project_id. This is not just a rename: CAPS vendors already use program_id for program flows (caps-be/src/vendors/midtrans/create.ts:59, caps-be/src/vendors/tupaggo/create.ts:41,108,124), so reusing it would collide with program mappings. The value is the donations projects.id (DB) / projectId (API/UI).
Comment 2 · fetch function name and reuse
“customFetchGateway — Why call it customFetchGateway? Why not normal fetchGateways()?”
“And we should create a function fetchGateways and then in fact use the same in PaymentGateways component too, instead of duplicating code.”
Applied. caps-ui gains src/functions/fetchGateways/, exported as fetchGateways(), following the existing checkStatus / refundOrder conventions. PaymentGateways is refactored to call the same function instead of its inline customFetch block. customFetch remains only the low-level HTTP primitive.
Comment 3 · generic caps-admin endpoint
“bx-be-nestjs : pf/caps/payment-gateways/donation-mapping — This should be a generic caps-admin endpoint not necessarily donation specific. Let it accept: 1. country 2. org 3. module 4. metadata (donation will pass here {donation_project_id:xxx}) 5. test.”
Applied. The endpoint is PUT /pf/caps/payment-gateways/mappings. It has no donation naming or donation-specific DTO fields. The body carries country, org, module, metadata, test, plus the ordered gatewayIds being synced (the “incoming gateway mapping list” from comment 5).
Comment 4 · no donations-be endpoint
“donation-be : donation/gateway-mapping — Again, we don’t need an endpoint for this. They have a single screen in their donations-fe screen which sends a lot of data and the gateway-mapping is a small part of it. We need just a service-method in their related module which will pass along the necessary info to bx-be-nestjs caps-admin generic endpoint.”
Applied. There is no POST donation/gateway-mapping route and no new donations-be DTO. The gateway selection is already part of the existing Amount-step save (PATCH /projects/:id, amountDetails.pgs). A service method in ProjectPgsService forwards the final saved rows to bx-be-nestjs from the existing save flow.
Comment 5 · delete and re-insert
“the reference implementation is not correct for the bx-be-nestjs endpoint. You also need to delete any existing mapping which matches the full metadata but is not part of incoming gateway mapping list. And existing values also, actually, it is good idea to delete and re-insert. Why? Because it keeps maintaining sort-order in mapping table simple, no?”
Applied. The sync is a full replacement of one metadata group, not an insert-missing diff. The endpoint deletes every row for the exact (entity_id, metadata) scope and re-inserts the complete incoming list in order. Removals and reordering become free; sort_order is written as 1..N (with one schema constraint change — see §6).

The revised solution

A donation project needs its own payment-gateway set. The same gateway (for example Stripe) can serve many projects, so it must be mapped once per project. The mapping row is scoped by metadata, and the donations-specific key is donation_project_id.

Mapping key
(entity_id, pg_id, metadata)
Donations metadata
{ "donation_project_id": <projects.id> }
Base / fallback group
rows with metadata IS NULL
Entity identity
(module, country, org) in caps.pg_entity
Donations identity
module = 'DX', country = project tenant code, org = project organization
Sync semantics
replace the exact metadata group (delete + insert all)

Action Item 1 — fetchGateways() in caps-ui

The draft proposed a new customFetchGateway that duplicated the only existing gateway fetch. The revised design extracts that fetch once and reuses it.

Current state (verified on origin/dev)

  • Only one gateway fetch exists: the inline block in caps-ui/src/components/PaymentGateways/PaymentGateways.tsx:28-65.
  • There is no fetchGateways and no customFetchGateway in caps-ui today.
  • FetchedGateways and validateGateways live in PaymentGateways.types.ts:41-67. A separate helper would either import from the component (wrong dependency direction) or copy the schema.
  • customFetch is the low-level primitive in caps-ui/src/utils/customFetch.ts:6-42. It is not the domain function.
  • caps-ui 2.5.1 is consumed by bx-fe as a pinned tarball (bx-fe/package.json:104); bx-fe has no app-level gateway fetch of its own.

2.3 The function

// caps-ui/src/functions/fetchGateways/fetchGateways.ts
import { customFetch, getCurrentLocale, setCurrentLocale } from "@/utils";
import { validateGateways } from "./fetchGateways.types";
import { FetchGatewaysProps, FetchGatewaysResult } from "./fetchGateways.types";

export const fetchGateways = async ({
  environment, country, currency, org, module, test, metadata, locale,
}: FetchGatewaysProps): Promise<FetchGatewaysResult> => {
  setCurrentLocale(locale);

  const response = await customFetch(environment, "/fetch-gateways", "POST", {
    country, currency, module, org, test,
    locale: getCurrentLocale(),
    metadata,
  });

  try {
    const body = await response.json();
    if (!response.ok) {
      return { error: body.error ?? "Could not fetch payment gateways from caps-be" };
    }
    if (!validateGateways(body.data)) {
      return { error: "Invalid gateway list response from caps-be" };
    }
    return { data: body.data as FetchedGateways };
  } catch (err) {
    console.error("Error while fetching payment gateways:", err);
    return { error: "Fetching payment gateways failed due to an unexpected error" };
  }
};
Why this shape checkStatus and refundOrder both call setCurrentLocale(), use customFetch(), and return { data } / { error }. fetchGateways matches that contract exactly, so it slots into the package with no new conventions.

Do not camel-case the metadata keys The existing PUT /pf/caps/entities/:id/config route runs SnakeToCamelMiddleware, which recursively converts nested object keys (bx-be-nestjs/src/_shared/middleware/snake-to-camel.middleware.ts:10-44). Do not register the middleware on this route; accept camelCase top-level fields (gatewayIds) and leave metadata untouched. If the admin UI must send snake_case, add an explicit skip for the metadata subtree instead of converting it.

3.4 Service

// payment-gateways.service.ts
async syncMappings(dto: SyncGatewayMappingsDto) {
  if (Object.keys(dto.metadata).length === 0) {
    throw new BadRequestException('metadata must be a non-empty object');
  }

  const entityId = await this.repository.findEntityId(
    dto.country, dto.org, dto.module,
  );
  if (!entityId) {
    throw new NotFoundException(
      `CAPS entity not found for ${dto.module}/${dto.country}/${dto.org}`,
    );
  }

  const gatewayIds = dto.gatewayIds.map(Number);
  if (new Set(gatewayIds).size !== gatewayIds.length) {
    throw new BadRequestException('gatewayIds contains duplicates');
  }

  const validIds = await this.repository.findValidGatewayIds({
    gatewayIds,
    test: dto.test,
  });
  const invalid = gatewayIds.filter((id) => !validIds.has(id));
  if (invalid.length > 0) {
    throw new BadRequestException(
      `Unknown, disabled, or test/live-mismatched gateway ids: ${invalid.join(', ')}`,
    );
  }

  const result = await this.repository.replaceMetadataGroup({
    entityId,
    metadata: dto.metadata,
    gatewayIds,
  });

  return {
    entityId,
    country: dto.country,
    org: dto.org,
    module: dto.module,
    test: dto.test,
    metadata: dto.metadata,
    deleted: result.deleted,
    inserted: gatewayIds,
  };
}

3.5 Repository — the delete-and-reinsert

// payment-gateways.repository.ts
async findEntityId(country: string, org: number, module: string) {
  const [row] = await this.txHost.tx
    .select({ id: capsPgEntitySchema.id })
    .from(capsPgEntitySchema)
    .where(and(
      eq(capsPgEntitySchema.country, country),
      eq(capsPgEntitySchema.org, org),
      eq(capsPgEntitySchema.module, module),
    ));
  return row?.id ?? null;
}

async findValidGatewayIds(params: { gatewayIds: number[]; test: boolean }) {
  if (params.gatewayIds.length === 0) return new Set<number>();
  const rows = await this.txHost.tx
    .select({ id: paymentGatewaysInCaps.id })
    .from(paymentGatewaysInCaps)
    .where(and(
      inArray(paymentGatewaysInCaps.id, params.gatewayIds),
      eq(paymentGatewaysInCaps.test, params.test),
      eq(paymentGatewaysInCaps.enabled, true),
    ));
  return new Set(rows.map((r) => Number(r.id)));
}

@Transactional()
async replaceMetadataGroup(params: {
  entityId: number;
  metadata: Record<string, unknown>;
  gatewayIds: number[];
}) {
  const { entityId, metadata, gatewayIds } = params;

  // 1. Delete exactly this metadata group — not the NULL/base group, not a subset.
  const deleted = await this.txHost.tx
    .delete(capsPgMappingSchema)
    .where(and(
      eq(capsPgMappingSchema.entityId, entityId),
      sql`${capsPgMappingSchema.metadata} = ${JSON.stringify(metadata)}::jsonb`,
    ))
    .returning({ id: capsPgMappingSchema.id });

  // 2. Insert the complete incoming list in order.
  if (gatewayIds.length > 0) {
    await this.txHost.tx.insert(capsPgMappingSchema).values(
      gatewayIds.map((pgId, index) => ({
        entityId,
        pgId,
        sortOrder: index + 1,
        metadata,
      })),
    );
  }

  this.auditLogger.info('CAPS gateway mapping group replaced', {
    event_action: 'update',
    event_type: 'entity_config',
    event_id: entityId,
    data: { metadata, gatewayIds, deleted: deleted.length },
  });

  return { deleted: deleted.length };
}
Companion changes required for safety Once metadata groups exist, the existing caps-admin entity screen must stop touching them:
  • saveConfig must delete only metadata IS NULL rows (entities.repository.ts:136-153 currently deletes all rows for the entity).
  • findMappings must return only metadata IS NULL rows (entities.repository.ts:106-118 currently returns only pgId for every row, so the UI cannot tell groups apart and would rewrite them as base rows).
Without these two fixes, the next caps-admin save silently wipes the donation mappings.

4.2 The service method

// donations-be/src/modules/projects/pgs/project-pgs.service.ts
public async syncCapsMappings(params: {
  projectId: number;
  organizationId: number;
  pgs: ProjectPgsSchemaSelect[];
  token: string;
  tenantCode: string;
}): Promise<void> {
  // One call per entity; project_pgs rows are already saved.
  const byEntity = new Map<number, ProjectPgsSchemaSelect[]>();
  for (const pg of params.pgs) {
    if (!pg.entityId || !pg.pgId) continue;   // entityId is nullable today
    const rows = byEntity.get(pg.entityId) ?? [];
    rows.push(pg);
    byEntity.set(pg.entityId, rows);
  }

  for (const rows of byEntity.values()) {
    await this.capsAdminClient.syncGatewayMappings({
      token: params.token,
      tenantCode: params.tenantCode,
      body: {
        country: params.tenantCode,          // tenant code is the 2-char country code
        org: params.organizationId,
        module: 'DX',
        test: env.CAPS_TEST_MODE,
        metadata: { donation_project_id: params.projectId },
        gatewayIds: rows
          .sort((a, b) => a.displayOrder - b.displayOrder)
          .map((pg) => Number(pg.pgId)),
      },
    });
  }
}

// donations-be/src/_shared/bx/bx-caps-admin.client.ts
@Injectable()
export class BxCapsAdminClient {

  public async syncGatewayMappings(params: {

    tenantCode: string;

      country: string; org: number; module: string; test: boolean;

      `${env.BX_BE_BASE_URL}/pf/caps/payment-gateways/mappings`,

      method: 'PUT',
      headers: {
        'Content-Type': 'application/json',
        Authorization: `Bearer ${params.token}`,

The sync logic — delete the group, re-insert everything

The draft's insert-missing-only logic cannot remove a gateway the admin deselected, and it needed extra diffing to keep sort order. The revised logic replaces the group atomically.

  1. Resolve the entity. Look up caps.pg_entity by (country, org, module). No entity → 404. Do not auto-create on a sync.
  2. Validate the incoming list. Reject duplicates. Every id must exist in caps.payment_gateways, be enabled, and have test = dto.test. Invalid ids → 400, before anything is deleted.
  3. Delete the exact metadata group. DELETE ... WHERE entity_id = :eid AND metadata = :metadata::jsonb. Exact JSONB equality — not a subset, not the NULL group.
  4. Insert the complete incoming list. One row per gateway, sort_order = 1..N in array order, same metadata object.
  5. Return the result. { entityId, metadata, test, deleted, inserted }. An empty incoming list is valid and just clears the group.
  6. Audit. Log the metadata scope, the full gateway id list, and the deleted count.

5.1 Insert-missing vs full replacement

CaseDraft (insert missing only)Revised (delete + insert all)
Add a gatewayInsert one rowGroup replaced; row present
Remove a gatewayStale row remainsRow gone
Reorder gatewaysSort order not updatedRe-inserted in new order
Re-run with the same listNo-opSame content; row ids change; vendor_history dedupes

5.2 Edge cases

  • Exact metadata scope. The delete matches the full object, e.g. only rows whose metadata is exactly {"donation_project_id":1127694}. Other projects and the base group are untouched.
  • NULL group. This endpoint never deletes metadata IS NULL rows. The caps-admin entity screen owns the base group.
  • Empty metadata object. Rejected. caps-be treats {} as matching every checkout (an empty object passes the every() check), which would suppress the NULL fallback. See §9.
  • Duplicates. Rejected before delete, so a bad payload cannot wipe the group.
  • Concurrent syncs. Both run in transactions; the unique key serializes conflicting inserts. If two saves race, the later transaction wins and the earlier one may roll back on the constraint — acceptable for an admin screen, but wrap the call with the repo's PG error handling and retry once.
Idempotency Re-running the same list leaves the same logical content. Row ids change because of the delete/re-insert, but the mapping key (entity_id, pg_id, metadata) and the sort order are identical. caps.update_vendor_history() is AFTER INSERT with ON CONFLICT DO NOTHING, so the re-inserts do not duplicate vendor history.
6

Sort order and the one schema constraint that matters

The reviewer's “delete and re-insert keeps sort order simple” is the right model, but the current schema has a global unique key that prevents two metadata groups from both using 1..N. This is the one migration the revised design needs.

6.1 Current constraints (verified)

ConstraintDefinitionEffect
pg_mapping_entity_id_sort_order_key UNIQUE (entity_id, sort_order) Global per entity. All metadata groups compete for the same numbers.
pg_mapping_entity_id_pg_id_key UNIQUE (entity_id, pg_id, metadata) Allows the same gateway for different projects. NULL metadata is treated as distinct (Postgres default), so duplicate NULL rows are technically possible.
pg_mapping_sort_order_check CHECK (sort_order > 0) Positions start at 1.

6.2 Recommended migration — per-group sort order

-- caps schema migration (source of truth: bx-be/db/migrations)
ALTER TABLE caps.pg_mapping
  DROP CONSTRAINT pg_mapping_entity_id_sort_order_key;

ALTER TABLE caps.pg_mapping
  ADD CONSTRAINT pg_mapping_entity_id_metadata_sort_order_key
  UNIQUE (entity_id, metadata, sort_order) NULLS NOT DISTINCT;

NULLS NOT DISTINCT requires PostgreSQL 15+. The bx database is on PG 15.8, so this is available. It makes the NULL/base group behave as one group instead of many distinct rows.

6.3 Fallback if the migration is not approved

Keep the global key and compute an offset after deleting the group: 

-- after DELETE of this metadata group
SELECT coalesce(max(sort_order), 0) FROM caps.pg_mapping
WHERE entity_id = $1;

-- insert the incoming list with sort_order = offset + 1 .. offset + N

This preserves the relative order inside the group (caps-be sorts all entity rows then filters by metadata), but the numbers are no longer 1..N per project. The migration is the cleaner long-term shape.

6.4 Do not “harden” metadata to '{}'

Correction to the source draft The draft suggested metadata NOT NULL DEFAULT '{}'::jsonb. Do not do that. caps-be treats an empty metadata object as matching every checkout (Object.keys({}).every(...) is vacuously true), so an empty object silently becomes a global mapping and suppresses the NULL fallback. Keep metadata nullable: SQL NULL is the base group; a non-empty object is a scoped group. If you want to close the NULL-distinct hole, use UNIQUE ... NULLS NOT DISTINCT instead of a default value.

How CAPS matches metadata (verified)

The revised design depends on caps-be's existing matching semantics. These are the exact rules in caps-be/src/db/rpc.ts:79-101.

  1. Load all rows for the entity, test mode, and enabled = true, ordered by sort_order.
  2. If no row has non-null metadata, return all rows (base mode).
  3. If any row has metadata, a row matches when every key in the row's metadata equals the incoming value with strict ===. The incoming object may carry extra keys (subset match).
  4. If at least one row matches, return only the matched rows. NULL-metadata rows are not added.
  5. If nothing matches, fall back to rows with metadata IS NULL.
  6. Append the synthetic paylater row afterwards.
Base group prerequisite For the donation picker to offer the full menu, the DX entity should keep a metadata IS NULL base group listing the gateways selectable for donations. A project-specific group then overrides it. Without a base group, once the first project group exists, /fetch-gateways for a new project matches nothing and falls back to an empty NULL set — leaving only paylater.

9.1 What the fetch does not do

  • It is not an unfiltered catalogue. currency is required and gateways that do not support it are dropped.
  • It does not return metadata. A client cannot tell which group produced a gateway.
  • pg_list is a caps-ui-side filter only. caps-be ignores it unless it is stored in a mapping row's metadata.
  • /create-order does not re-validate the mapping. Once the client picks a pgId, caps-be looks the gateway up by id and trusts it; metadata matching happens at list time, not order time.
Strict equality, not JSONB semantics dbMeta[key] === incomingMeta[key] is JavaScript strict equality. Numbers and strings do not match (1 vs "1"), and arrays/nested objects never match because the JSON-decoded references differ. donation_project_id must be a JSON number on both sides — which it is when both the stored metadata and the fetch metadata come from the same projects.id number.
